# T104 - Accept Markdown with local images without a hand-built ZIP

## Objective

Let users convert a Markdown file that references local images by selecting or dropping the Markdown file together with its images (or a folder), instead of building a ZIP by hand.

Created from the repository analysis accepted by the owner on 2026-10-09 (section: what to change, item 3).

## Acceptance criteria

- Browser 2docx and 2pptx workspaces accept a multi-file or folder selection and drag and drop; the CLI accepts a Markdown path and collects the referenced local images.
- The browser or CLI client packages the files client-side into the existing approved archive boundary and the HTTP input contract is unchanged (D2); all archive, path, image, SVG, size and count limits and ClamAV scanning still apply.
- Missing or escaping image references produce the existing stable validation errors.
- Unit, integration and final-image E2E tests in both profiles cover the primary path, missing image, path traversal and oversize cases.
- Update the conversion UI, CLI and capability documentation.

## Progress

- 2026-10-09: Created in Linear and mirrored here from the owner-accepted repository analysis.
  Not started.
- 2026-10-10: Implementation started on branch `feat/T104-markdown-local-images`. The 2docx and
  2pptx workspaces accept multi-file, folder, and dropped-folder selections and package the
  Markdown file with its referenced local images in the browser; `markweave convert` packages a
  Markdown path's referenced local images. Both build the approved layout (root `document.md`
  plus referenced images, stored ZIP), keep the HTTP input contract unchanged, and pre-check
  missing, escaping, and invalid references with the service's stable validation messages, which
  a shared fixture ties to the service parser. Unit, integration, and final-image E2E coverage
  (CLI workflow and a new browser test in both profiles) is added; documentation is updated.
  Awaiting hosted CI, final-image E2E evidence, and independent review.
- 2026-10-10: Review round 1 found that the two hand-written client parsers diverged from the
  service parser. Owner decision A2: the CLI reuses the service's reference and path module,
  extracted to `markweave.conversion.image_references`, through a new optional
  `markweave[packaging]` extra; the base CLI stays standard-library only and asks for the extra (or
  `--no-package`) when Markdown contains image syntax. Owner decision B2: the browser uses pinned
  markdown-it 15.0.2, markdown-it-footnote 4.0.0, and yaml 2.9.0 with the service's front-matter
  rule, checked against a fixture generated by the service parser; only referenced images are
  packaged. Regression tests cover multiline and container reference definitions, list-indented
  code, and HTML entities in both clients.
- 2026-10-11: Review round 2 fixes. The CLI always runs the shared parser when the `packaging`
  extra is installed, so YAML escapes that decode into image syntax are packaged; without the
  extra, Markdown with `![` or with front matter containing a backslash escape asks for the extra.
  The CLI opens every image path component relative to an open parent directory descriptor with
  `O_NOFOLLOW`, so any symbolic link in an image path, including an ancestor swapped in after
  resolution, is refused with the stable escaping error. Before reading images it reads the
  service's upload limit and refuses an oversize package with `conversion_request_invalid`. The
  browser keeps YAML scalar semantics (block, folded, quoted, escaped) for metadata its stricter
  parser reports errors in, so multiline metadata references are packaged when selected. The
  parity fixture gains these cases. The audited pnpm package-set pin now includes the eight
  approved browser packages. Awaiting hosted CI and independent review.
- 2026-10-11: Review round 3 fix. The CLI opens the Markdown file's directory once, before reading
  the Markdown, reads the Markdown relative to that descriptor with `O_NOFOLLOW`, and reuses the
  same descriptor for parsing, the upload-limit lookup, and image collection; the base directory
  is never reopened by pathname. Regressions replace the Markdown directory and an ancestor with
  an outward symbolic link during the upload-limit lookup and prove that only the anchored tree's
  bytes are packaged. Awaiting hosted CI and independent review.
